# Football Manufacturing, Export, Industry Intelligence & E-Commerce Management System

A university **Database Management Systems** lab project. A Microsoft SQL Server database sits at the center
of the system; a FastAPI backend exposes it as a validated REST API; a React frontend consumes that API for a
public company directory, a customer marketplace, and a role-based admin panel; n8n automates a handful of
notifications on top.

Everything runs on **localhost** — no cloud services, no real payment gateway, no fabricated company data.

## Features

- **Company Directory** — real, publicly-known Sialkot/Pakistan football manufacturers, clearly labelled
  Verified / Estimated / Synthetic
- **Manufacturing** — manufacturers, employees, suppliers, raw materials, products, production batches
- **Quality Control** — 6-point inspection per batch; failed batches never become sellable inventory
- **Inventory** — per-warehouse stock, automatic low-stock flagging, DB triggers preventing negative stock
- **Export Management** — buyers, multi-line export orders, shipment tracking, payment/export status workflow
- **Marketplace** — customer registration, browsing/search/filter, cart, simulated checkout, order history, reviews
- **Analytics & Reports** — live dashboard, revenue by country, top markets, production summary, company
  comparison, a transparent (non-official) manufacturer ranking
- **Automation** — n8n workflows for low-stock alerts, new-order and shipment notifications, weekly digests
- **Authentication** — JWT, bcrypt password hashing, 5 employee roles + customer accounts, role-gated endpoints

## Technology Stack

| Layer | Technology |
|---|---|
| Database | Microsoft SQL Server 2022 (SSMS for management) |
| Backend | Python 3, FastAPI, SQLAlchemy + pyodbc, Pydantic, JWT, bcrypt |
| Frontend | React (JavaScript, not TypeScript), Vite, React Router, Axios, Tailwind CSS, Recharts |
| Automation | n8n |

## Architecture

```
React (localhost:5173)  →  FastAPI (localhost:8000)  →  SQL Server (FootballIndustryDB)
                                     ↑↓
                              n8n (localhost:5678)  →  Email/Slack/etc.
```

The database is not a passive data store — 3NF normalization, 6 stored procedures, 3 triggers, and 7 views do
real work (computing order totals, gatekeeping inventory behind QC passes, preventing negative stock) that the
API layer relies on rather than re-implements.

## Quick Start

### 1. Database

Open SSMS, connect to your local SQL Server instance, and run each file in `database/` **in numeric order**
(01 through 09), using **F5**. Full details: `database/README.md`.

### 2. Backend

```bash
cd backend
python -m venv venv
source venv/bin/activate        # venv\Scripts\activate on Windows
pip install -r requirements.txt
cp .env.example .env            # copy .env.example .env on Windows
# edit .env: set DATABASE_URL and SECRET_KEY
python -m app.utils.generate_demo_hashes    # then run the printed UPDATE statements in SSMS
uvicorn app.main:app --reload --port 8000
```

API: http://localhost:8000 · Swagger: http://localhost:8000/docs

### 3. Frontend

```bash
cd frontend
npm install
cp .env.example .env            # copy .env.example .env on Windows
npm run dev
```

Site: http://localhost:5173

### 4. n8n (optional but recommended for the automation requirement)

```bash
npx n8n
```

n8n: http://localhost:5678 — import the 4 workflows from `n8n/workflows/` and follow `n8n/README.md`.

See `database/README.md` for the full breakdown. In short: manufacturer **identity facts** (name, city,

industry; all **financial and transactional figures** are synthetic, generated purely to give the database

## DBMS Concepts Demonstrated (Viva Prep)

**Why 3NF?**
Every non-key column depends on the whole primary key and nothing else — e.g. `ExportOrder` doesn't store a
client's country (that depends on `ClientID`, not `ExportOrderID`); it's joined from `Client` instead. This
eliminates update anomalies: change a client's country once, and every order automatically reflects it.

**Why PK/FK relationships?**
Primary keys give every row a stable identity; foreign keys enforce that an `OrderDetail` can never reference
a `Product` that doesn't exist, and `ON DELETE`/`ON UPDATE` rules define what happens to dependent rows —
e.g. deleting a `ProductionBatch` cascades to its `QualityInspection`, but a `Product` can't be hard-deleted
while `ProductionBatch` rows reference it (`ON DELETE NO ACTION`), forcing the soft-delete pattern the API
uses instead.

**Why views?**
`vw_ExportRevenueByCountry`, `vw_LowStockProducts`, etc. encapsulate multi-table joins and aggregations behind
a single, stable name — the API and any future reporting tool queries `vw_LowStockProducts` without knowing
or caring that it's really a 3-table join with a `WHERE` clause.

**Why stored procedures?**
`sp_PlaceExportOrder` guarantees an order header and its line items are inserted together, atomically, with
validation and error handling — logic that would otherwise have to be duplicated (and could drift) across
every client that places an order.

**Why triggers?**
`trg_UpdateOrderTotal` keeps `ExportOrder.TotalAmount` correct automatically, no matter which application
(this API, a future admin tool, even a raw SSMS query) modifies `OrderDetail` rows. `trg_PreventNegativeInventory`
is a database-level safety net that holds even if a future client forgets to check stock before deducting it.

**Why transactions?**
Placing an export order touches two tables (`ExportOrder`, `OrderDetail`) plus a `Shipment` insert — if the
line-item insert fails partway through, `ROLLBACK` ensures you never end up with an order header and no
items, or vice versa.

**Why indexes?**
Foreign-key columns (`ProductID`, `ManufacturerID`, etc.) are queried constantly via joins; without a
nonclustered index, SQL Server would table-scan `OrderDetail` every time it looked up a product's export
history.

**Why FastAPI?**
Async-capable, auto-generates OpenAPI/Swagger documentation from Pydantic type hints, and its dependency
injection system (`Depends(require_roles(...))`) made role-based access control straightforward to apply
consistently across 37 endpoints.

**Why SQL Server?**
Widely taught, free via SSMS/Developer Edition, and its T-SQL feature set (window functions, computed
columns, `TRY/CATCH`, table-valued parameters) covers everything the syllabus asks for.

**Why React?**
Component reuse (one `DataTable` component powers a dozen different admin screens), and its ecosystem
(React Router, Axios, Recharts) mapped directly onto the project's page-count and charting requirements.

**Why n8n?**
Visual, self-hostable workflow automation — lets the notification logic (low stock, new orders, shipment
updates) live outside the core application code, which is closer to how real logistics/ERP systems separate
"what happened" from "who gets told about it."

**How does the database connect to the website?**
`React → Axios (HTTP/JSON) → FastAPI → SQLAlchemy (mssql+pyodbc) → SQL Server`. The frontend never talks to
the database directly; every number on the dashboard is the result of a live query, view, or stored procedure
call made by the backend in response to an API request.
